# Shard map for the filtered-proxy smokes.
#
# Each line: <shard-name> flows <flow>...
#
# A shard is a subset of the flows that one CI job runs. The split exists because
# the two halves are independent: flows 10 and 20 exercise the session-layer
# proxy with Claude Code and Codex, flows 30 and 40 exercise the agentd-owned
# OpenCode relay — disjoint subnets, disjoint harnesses, disjoint Go packages.
# Running them as two jobs halves the wall-clock and lets each job install only
# the harnesses it actually launches.
#
# HARNESSES ARE NOT DECLARED HERE. Each flow declares what it launches, in its
# own file (`flow::harnesses`), and each shard's install set is DERIVED as the
# union of its flows' declarations. That is why a shard line names flows and
# nothing else: there is no second list to keep in step, and moving a flow to the
# other job moves its harnesses with it. A `harnesses` key left in this file is
# refused BY NAME rather than ignored — a stale line silently skipped would read
# as a declaration that had taken effect.
#
# The split is at the JOB level, not inside one run. `fixture::hosts_add` and
# `fixture::hosts_restore` (scripts/lib/smoke/fixture.sh) mutate /etc/hosts
# through a single shared backup file, so two flows running concurrently in one
# process would clobber each other's resolver state. Do not try to parallelise
# within a shard.
#
# THE GUARD: run.sh refuses to run unless the union of every shard's flow list
# covers every flow the manifest names, and unless the harnesses those flows
# declare cover every harness lib/harnesses.sh knows how to install. A flow that
# belongs to no shard would silently stop running while both CI jobs stayed
# green — the vacuous shape the evidence discipline exists to refuse — and a
# harness no flow declares would be installed by nobody while the flow needing it
# failed with "not found". A flow declaring no harness set AT ALL is refused too:
# a flow that launches none says `none`, so "launches nothing" and "the author
# forgot" cannot look alike. All of these are self-tested in
# scripts/lib/smoke/selftest.sh, which every run executes before trusting
# anything, so the guards cannot rot unnoticed either.
#
# A third check closes the level above: run.sh reads the workflow files and
# refuses to run unless the shard names CI's matrix invokes are exactly the ones
# declared here. A shard added below but not to the matrix would otherwise
# satisfy both unions above and still execute nowhere.
#
# Adding a flow therefore costs three edits, all reviewable: a manifest.txt line
# saying what evidence it must produce, a shards.txt entry saying which job runs
# it, and a `flow::harnesses` declaration in the flow saying what it launches.
# Forgetting any of them fails validation rather than passing quietly — and, for
# the harness set, rather than failing later and somewhere else.
